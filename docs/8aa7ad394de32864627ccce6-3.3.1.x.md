## Session — 2026-10-25 — Issue #115 (Net/ZNet: primary + mirrors drop UDP events)

**Trigger:** issue #115 — with several Net/ZNet entries (one primary + mirror
entries), sensor events stop arriving on the primary. Debug logs show one
entry logging 1,200+ "ignoring packet from … (expected …)" lines while every
other entry logs "no packets from … in 70s". Reloading the primary "fixes" it
until the next restart. `debug_connection` reports "Connection: OK" the whole
time. Also reported: `ERROR [homeassistant.core] Unable to remove unknown job
listener` when reloading an entry.

### Root cause

Every config entry created its own `TellStickNetController` with its own UDP
socket bound to port 42314 (all with `SO_REUSEADDR`). A unicast datagram is
delivered to only **one** of those sockets — in practice the one bound last —
so only one entry ever received traffic, and its `_event_loop` dropped every
datagram whose source IP was not its own host. Which entry "wins" depends on
startup/reload order, so the symptom moves around. This also defeated mirror
forwarding: a mirror's socket swallowed the primary's packets (and vice versa).

### Fix applied

1. **Shared UDP listener (`_NetUdpHub` in `net_client.py`)** — all Net/ZNet
   controllers share one socket (still port 42314, ephemeral-port fallback
   preserved). One receive loop dispatches each datagram **by source IP** to
   the controller(s) registered for that host; unknown sources are dropped
   with a debug line. The socket is reference-counted: it opens with the first
   subscriber and closes with the last, so entries can be added/reloaded/
   removed independently. Controllers no longer bind sockets; `connect()`
   subscribes + sends `reglistener`, `disconnect()` releases. Datagrams
   arriving between `connect()` and `start_event_listener()` are buffered and
   flushed (preserving the old kernel-buffering behaviour). Idle "no packets
   from X in 70s (waiting…)" logging is preserved per host in the hub.
2. **`debug_connection` now shows "Last packet received"** per Net/ZNet entry
   (timestamp, age, packet count) so a silently starved entry is visible
   instead of a bare "Connection: OK" (explicitly requested in #115).
3. **Fixed "Unable to remove unknown job listener" on reload** — the
   `EVENT_HOMEASSISTANT_STARTED` one-shot listeners (primary + mirror paths)
   are no longer wrapped in `entry.async_on_unload()`. They remove themselves
   when they fire; removing again at reload logged the error. A leftover
   listener is harmless (`reconnect()` is a no-op on a disconnected controller).

## Session — 2026-11-02 — Issue #114 (Net v1 send drops: event listener collides with command socket)

### Root cause

The v1 Net firmware opens its per-listener event socket on the registrant's
source port. The shared listener bound UDP 42314 first, so the firmware's event
socket collided with its own command socket on 42314 and later `send` commands
were silently dropped. The reporter's probe (`tools/probe_net_send.py`, phases

registering from an ephemeral port worked.

  The 42314 bind and its fallback are removed. `reglistener` and all commands go

  events.
- The constructor `port` argument is now unused; kept so `tests/test_net_udp_hub.py`

## Session — 2026-11-03 — Hotfix: app-config import aborted by an unhashable dict (3.3.1.10)

**Trigger:** report from the `3.3.1.9.20261103213025` dev build:
`App-config device import skipped due to error (setup continues): cannot use
'dict' as a set element (unhashable type: 'dict')`.

### Root cause

The #126 fix added `registered_ids = set(device_id_map.values())`. On a Duo
entry that map holds integer telldusd ids **except** for `luxorparts` and

Keep only integer values when building the lookup set. Dict values are not
telldusd ids, so they are irrelevant to the comparison.

## Session — 2026-11-04 — Proof-of-concept blind replay for issue #100 (3.3.1.11)

**Goal:** find out on real hardware whether the three payloads captured in issue
#100 can drive the Kjell / Tuya curtain motor, before any cover support is written.

### Why a service rather than an entity

Neither Duo nor ZNet can *receive* this remote: the firmware only reports packets
that one of its compiled decoders accepts, so the frames are dropped with no
event and no LED. There is therefore no state feedback and no auto-discovery —
replay is the only route, and it is Duo-only (`tdSendRawCommand`). A fake cover
entity would imply a state that cannot exist, so the PoC is a service that can be
deleted in one commit.

### Frame model (rtl_433 captures, 2026-04-27)

- preamble: mark 1460 µs, sync gap 1524 µs
- bit 1 → short mark 380 µs + long gap 744 µs
- bit 0 → long mark 776 µs + short gap 348 µs
- 40 bits, ~47 ms per frame, ~5 frames per button press

Polarity was derived, not assumed: the `…ee` capture carries 16 one-bits against
14 for `…aa`, and shows exactly two more short marks and two more long gaps.
Variants b–d are kept because a replay attempt is how this gets confirmed.

### Payloads

`aa` = down, `ee` = up, `e1` = stop (last byte is the button). The labels in the
issue contradict each other, so the mapping is probable only.

### Limits found

- Tick quantisation is 10 µs and saturates at 255 (2550 µs), so the 16 ms gap
  between frames cannot be represented: replay one frame and let `R<n>` repeat.
- 82 timing elements → 82 tick bytes → 88-byte command.

### Verification

- New `tests/test_poc_blind.py`: bit expansion, timing structure, tick range,
  command framing, distinct commands per button, clamping and error paths.
- `tests/test_ha_integration.py` passes; py_compile and pyflakes clean.
- Runtime copy re-synced; `diff -rq` identical.

### Version

3.3.1.10 → **3.3.1.11** in both manifests.

### Not verified

No hardware was available, so nothing here proves the blind obeys any variant.

## Burst replay fix — 2026-11-04 (3.3.1.14)

Variants a–d moved nothing, so the RTL-SDR log attached to issue #100 was
re-read frame by frame. The payloads are genuine over-the-air captures
(`{40}6c82050eaa`, `…eee`, `…ee1`) — never Telldus Live values; no TellStick can
receive this remote at all. The defect was the **replay structure**, not the
codes:

- **A press is five frames, not one.** Every multi-frame capture shows five
  identical 40-bit frames per press with 16352 µs of silence between them (205
  pulses over 321 ms), while the PoC sent frames 2 ms apart (`P\x02`).
- **Each frame starts with a ~4.9 ms mark**, not 1.46 ms. The 1460 µs value in
  the single-frame decodes is the same pulse clipped by the recorder: frames
  inside a burst report 4876 µs.
- A timing byte saturates at 2550 µs, so the 4.9 ms start mark is emitted as
  `2550 + 10 + 2340`; the 10 µs seam is far below the slicer resolution of any
  433 MHz OOK receiver.

### Changes

- `const.generic_rf_build_raw_command()` gained `pause_ms` (default 2 ms, so
  Luxorparts and the other generic-RF platforms are unchanged).
- `poc_blind` now defaults to `P\x11 R5` — five frames, 17 ms apart — and
  variant `a` uses the 4.9 ms frame start.
- Variants `c`/`d` reverse the 40 bits (polarity can be read off the pulse
  counts, bit order cannot) and `e`–`h` keep the old 1.46 ms frame start, for
  eight variants in total.
- New service `tellstick_local.poc_sweep_blind` transmits all eight variants of
  one button in sequence, with a configurable pause, for a pairing test.
- The Add-device step gained a **gap between frames (ms)** field and defaults to
  5 frames / 17 ms; `cover.py` stores and uses the pause per device.
- USER_GUIDE §5.3 rewritten: motor must be in learn mode, burst explanation,
  variant sweep, the new action and the removal of the old "repeat 10".
- `strings.json` / `translations/en.json` updated; both still parse as JSON.

## Correction — 2026-11-04 — the remote is already paired (3.3.1.16)

The 3.3.1.14 notes and the user guide told testers to put the motor in **learn
mode** first. That was wrong: the captures come from the motor's own, **already
paired remote**, so the motor knows this code and a faithful replay needs no
learning step at all. The pairing advice is removed from USER_GUIDE §5.3 and from
the Add-device step description; the guide now says plainly that a replay the
motor ignores is a waveform problem, not a pairing problem.

That narrows the remaining suspects to the waveform itself, which is what the
3.3.1.14 fix already targeted:

- five frames per press with ~16.4 ms between them (was 2 ms),
- a ~4.9 ms frame-start mark (was 1.46 ms — a clipped burst edge),
- eight frame variants, now that bit *order* is a separate unknown from polarity.

**Open question recorded from the captures:** in the "up" capture rtl_433
printed three frames of `6c82050eee` followed by one `6c82050ee1`. If that last
byte is a counter rather than a button code, a replayed frame goes stale and even
a perfect replay would only match the press it was captured from. Nothing here
