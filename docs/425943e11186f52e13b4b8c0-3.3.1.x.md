## Session — 2026-10-25 — Issue #114 investigation (original TellStick Net, no TX)

**Trigger:** issue #114 — on the *original* TellStick Net (v1, C firmware),
devices add fine and `send` UDP packets leave Home Assistant, but the device
never transmits (no LED blink, receiver silent) while Telldus Live works.
Two reporters (fw 4 and fw 17). Not reproducible by the maintainer.
Investigation only — no integration code changed.

### What was investigated

1. Byte-exact comparison of our UDP `send` packet against Telldus' own
   reference client (`telldus/tellstick-net/client/send.py`) and the official
   protocol doc (archived `developer.telldus.com/doxygen/html/TellStickNet.html`).
2. Byte-exact simulation of the published v1 firmware parser
   (`firmware/livemessage.c`, `tellsticknet.c::send()`,
   `transmit_arctech.c`) against our real `encode_packet()` output.
3. RF frame comparison: `transmit_arctech.c::sendArctechCommand()` vs
   telldus-core `ProtocolNexa::getStringSelflearningForCode()` (from
   `telldus-core_2.1.3-beta1.orig.tar.gz` in this repo).
4. Cross-checking third-party evidence (molobrakos/tellsticknet issues #23/#27,
   PR #27) for which packet forms were ever confirmed on which hardware.

### Findings

- **Our packet is correct.** Structure is byte-identical to Telldus'
  `client/send.py`; the simulated firmware parser extracts
  house=292130/unit=0/method=1 and reaches TX; the RF frame matches
  telldus-core bit for bit (unit is 0-indexed on the wire — we already
  compensate).
- **The non-reproduction is a hardware/firmware-generation gap:** all TX
  verification in this project happened on the Python-firmware units
  (Net v2 / ZNet). The v1's open-source firmware is a development build
  (`FIRMWARE_VERSION "X"`); Telldus' own send client refuses production
  firmware, and no third party has confirmed the native arctech dict on a
  production original Net (the "works like a charm" report was a ZNet v2;
  the confirmed v1 send was raw S bytes).
- **`P`/`R` repeat parameters have three inconsistent placements on record**
  (dict keys per the official doc and the open firmware; trailing flat pairs
  per molobrakos PR #27, whose "snappier" report implies the production
  firmware reads them from there). Our packet omits them entirely.
- Minor pre-existing gap: `learn` via the v1 native dict sends an OFF frame
  (`method != 1` → `sendZero()`), while telldus-core encodes learn as an ON
  frame. Pairing via the v1 native path is therefore wrong-though-often-tolerated.

### Artifacts

- `docs/NET_V1_SEND_INVESTIGATION.md` — full analysis, evidence table,
  ranked hypotheses and the outcome→fix matrix.
- `tools/probe_net_send.py` — standalone probe (stdlib only, run from any LAN
  machine) that sends five TX variants (native dict ± P/R in dict/trailing,
  raw S ± P/R), asks for LED/receiver observations per variant, then listens
  30 s for RF events to discriminate "send dropped" from "UDP delivery broken".
