## Session — 2026-11-18 — TellStick Net v1: full Duo protocol support

**Trigger:** issue #130. The reporter (tomwickstromse, original TellStick Net v1,
firmware 17) confirmed on 2026-11-17 that **dimming works** in
`3.3.3.1.20261111221006` — the release that sent arctech dim as a raw `S`
pulse train. That is the proof the v1 C firmware replays arbitrary pulse bytes
via `rfSend()`, so every Duo protocol can now work on a v1. This branch ports
them all.

### Why v1 is special

`tellsticknet.c :: send()` has two paths: a native dict handler that accepts
only `protocol=arctech` + `model=selflearning` (on/off, no dim, no level), and a
raw player that copies an S-only packet into `sendPacket[200]` and plays it on
the RF chip with `DEFAULT_REPEATS 10` / `DEFAULT_PAUSE 11`. v2/ZNet have the
opposite constraint (`handleSend()` ignores `S` and crashes without
`protocol`), so **only a v1 takes the raw path** — selected by the UDP discovery
product name `TellStickNet`.

### Implementation

- `net_client.py` — new "Net v1 raw pulse-train encoders" section: arctech
  (selflearning on/off/dim/learn/bell + code-switch + bell), comen, everflourish,
  sartano, yidong, waveman, upm, fuhaote, brateck, risingsun (selflearning and
  code-switch), x10, hasta (v1 and selflearningv2, with their R/P values), ikea
  (Koppla) and silvanchip (KP100 and Ecosavers).
- Every encoder is a port of the telldus-core implementation the **Duo** path
  uses, with the telldus transport markers removed: the leading `S` (raw-send
  opcode) and the trailing `+` (frame terminator) are Duo wire syntax, not RF
  timings. arctech follows molobrakos `protocols/nexa.py`, the layout already
  proven on this reporter's hardware.
- **Source parity checked:** the add-on builds `erik73/telldus` master
  (`tellsticklive/Dockerfile:38`, telldus-core `PACKAGE_VERSION 2.1.3`); every
  `service/Protocol*.cpp` there is **byte-identical** to the
  `telldus-core_2.1.3-beta1.orig.tar.gz` in this repo, so the ports are the Duo's
  own encoders. The Dockerfile patches touch only Nexa *learn* repeats for the
  Duo PID and binary-safe IPC — not protocol encoding. (The Duo learn patch is
  five sends of an `R=2` frame = 10 ON frames, which is exactly the v1 default
  repeat count, so a single raw ON packet matches it.)
- `_send_rf()` — raw-first routing when the product is `TellStickNet`; the
  firmware-dict chain below it is untouched, so v2/ZNet packets do not change.
  An explicit per-device `native` / `native_nofix` encoding still overrides the
  raw path for testing.
- Guards: frames over 199 bytes are refused (the firmware's `sendPacket[200]`
  would truncate them), and a raw packet carrying `protocol`/`model` is refused
  before it is sent, since the v1 handler returns before RF in that case.
- `send_raw_command()` on the Net controller — translates the Duo wire form
  `P<pause> R<repeats> S<pulses> +` into the v1 packet keys. This is what makes
  our **Duo-path additions** work on a v1, because they are all raw senders that
  telldus-core never had: `luxorparts` (pre-captured LPD codes), `generic_rf`
  record & replay (switches, lights, covers) and the Tuya/Kjell curtain motor.
  On v2/ZNet it logs and returns -1 rather than pretending to transmit.
- `config_flow.py` — the curtain-motor flow no longer aborts on every Net
  backend: a v1 (`product == "TellStickNet"`) is allowed through, ZNet / Net v2
  still abort with `poc_requires_duo`.
- `const.py` — `NET_RAW_PROTOCOLS` now lists every protocol with an encoder.
  `kangtai` is deliberately absent: it exists only in the ZNet Python firmware,
  not in telldus-core, so the Duo cannot send it either.
- Per-protocol repeat/pause: only risingsun sets them (`P=5`, `R=50` for
  learn) — the values telldus-core puts in its own Duo string. hasta and every
  other protocol use the firmware defaults, exactly as the Duo does; hasta was
  initially given the ZNet firmware's `R=10 P=25` and that was removed.

### Verification

- `python tests/test_net_protocol_encoding.py` → **ALL TESTS PASSED** (162
  checks). New Test 3b covers all 20 protocol/model/method cases: frame length,
  leading timing bytes, S-only invariant (keys ⊆ `S`/`R`/`P`), the 199-byte
  limit, hasta and risingsun R/P values, and that unsupported methods/models
  return `None` instead of a malformed frame.
- `python tests/test_ha_integration.py` → **ALL TESTS PASSED**.
- Mirror copies byte-identical (`diff -rq … --exclude=__pycache__` empty).
- arctech selflearning on/off/learn frames remain byte-identical to the
  molobrakos layout; the dim frame is still the 147-byte one confirmed on
  hardware, and on/off for arctech devices is unchanged for v2/ZNet.

### Not verified

- Real hardware per protocol. Only arctech on/off (native) and arctech dim (raw)
  are confirmed on an actual v1; luxorparts, generic_rf replay and the curtain
  motor are confirmed on a Duo only, and their v1 translation is checked at the
  byte level (Test 3c) but not on hardware. hasta, ikea, silvanchip, x10, risingsun,
  sartano/fuhaote/brateck/yidong/upm/waveman and comen raw frames are
  byte-for-byte ports, but no receiver has been exercised yet.
- Discovery-dependent gating: if a v1 unit cannot be identified (UDP discovery
  blocked by a VM/NAT), it keeps the old firmware-dict behaviour and the new
  protocols stay silent. The debug log reports the chosen path per send.
