## Session — 2026-10-23 — Legacy hardware future-proofing research

**Trigger:** the goal was to make existing TellStick Net/ZNet hardware
future-proof — full protocol support with no dependence on Telldus Live —
without introducing new hardware. This session was research only; no
integration, code or README changes were made.

### What was investigated

1. Whether the ZNet firmware is exploitable via PHP vulnerabilities.
2. Whether the firmware could be replaced with a community build.
3. Whether a device-local plugin could restore full protocol support.
4. Whether the device's local REST API could bypass the UDP limitations.
5. Why prior projects (HA `tellduslive` local mode, openHAB, Node-RED,
   WebThings, MQTT plugin) stalled.

### Findings

- **No PHP exists on the device.** The firmware rootfs (SquashFS at `0x130ad8`,
  3 290 files) contains no `php` binary and no `.php` files. The web UI is
  Python 2.7 + CherryPy 3.7.0 + Genshi 0.7. PHP CVEs are not applicable.
- **The plugin route is closed in practice.** `pluginloader/Loader.pyc`
  verifies plugins against `/etc/upgrade/plugins.keyring`, and Telldus must
  enable local plugins and approve a developer key per device.
- **The local REST API is vendor-gated.** `/api/authorize` redirects to
  `/web/login`, and the only `IWebRequestAuthenticationHandler`
  implementation is `tellduslive/web/WebRequestHandler.pyc` (Telldus OpenID,
  `login.telldus.com`, python-openid). Tokens have a maximum one-year TTL and
  cannot be reissued once that identity service disappears.
  Confirmed on hardware:
  `curl -i http://192.168.1.2//api/authorize?token=test` → `303` →
  `/web/login`, `Server: CherryPy/3.7.0`.
- **The RF stack is complete; only the network shim is broken.** `rf433/RF433.pyc`
  passes full parameters, a real `level`, and `R`/`P` prefixes to
  `stringForMethod()`; `productiontest/Server.pyc :: handleSend()` does not.
  The protocol gap is that one function.
- **Firmware upgrades are GPG-signed** (`/etc/upgrade/telldus.gpg`), so a
  community image cannot arrive over the air; flashing needs UART/U-Boot.

### Conclusion

The unauthenticated UDP socket is the only interface with no vendor dependency.
Future-proofing therefore means fixing `handleSend()` (patched module in the
writable overlay) or replacing the firmware outright — both requiring one root
shell per unit. The plugin and API routes are documented dead ends, not
untried ideas.

[`ZNET_LOCAL_ACCESS_RESEARCH.md`](ZNET_LOCAL_ACCESS_RESEARCH.md).
